# 定期実行（週1の巡回）

## いつ・何が動くか

毎週月曜 03:17 JST に、GitHub Actions の `Crawl`（`.github/workflows/crawl.yml`）が本番（Supabase）の DB に対して
`pipeline crawl` を流す。段は次の順。

1. `pipeline link-related`: 前回の巡回で主たる URL が死んだ制度に関連 URL を加える
2. `pipeline register-index`: 主たる URL の親ディレクトリを一覧ページの起点として登録する
3. `pipeline crawl`: 時刻の来た URL（一覧ページも）を取る
4. `pipeline suggest-moves`: 主たる URL が死んだ制度の移転先の候補を、一覧ページのリンクから作る。DB を読むだけで書かない。
   候補のファイルは成果物 `move-candidates` として90日残る

関連 URL の登録が失敗しても起点の登録と巡回は流れ、起点の登録が失敗しても巡回は流れ、巡回が警告で失敗しても候補づくりは流れる
（ジョブは失敗のまま赤く残る）。ビルドが失敗したときは、どれも流れない。
Actions の `schedule` は混み具合で起動が遅れることがある。

ジョブは GitHub のランナーではなく、東京（`ap-northeast-1`）の AWS CodeBuild をランナーにして動く。
DB（Supabase）と同じ東京で動かし、1件ごとの DB との往復を短くするため（米国のランナーでは毎分100件前後で頭打ちになっていた）。
作り方は [crawl-runner.md](crawl-runner.md)。steps・ログ・実行サマリー・通知は GitHub のまま。

実行は `crawl_runs` に残る。`kind` は、`schedule` で起きたものが `scheduled`、手で流したものが `manual`。

## どの URL が取られるか

時刻（`urls.next_crawl_at`）の来た URL と、48時間以内に来る URL（`--due-within-hours 48`）。
次の時刻は「取得した時刻 + 間隔」なので、余裕が無いと、今週の起動が先週より数分早いだけで7日間隔の URL が
「まだ」になり、次の週まで待つことになる。48時間は、起動のずれと、失敗に気づいて翌日に流し直したぶんのずれを吸収する幅。
再試行を待っている URL には当てない（バックオフと `Retry-After` はそのまま守る）。

`link-related` が加えた関連 URL は、登録した回の巡回で初めて取られる（新しい URL は時刻が来ているため）。
そのあとは普通の URL と同じ間隔で回る。

### 一覧ページ

制度の主たる URL（`registry`・`discovered` の両方。生死は問わない）の親ディレクトリ（`…/dir/`）を、`register-index` が
`role = 'index'`・深さ0・優先度90で `urls` に入れる。既にある行は触らない。起点のページのリンクはたどらず、`…/dir/index.html` も試さない。
一覧ページのリンクは、内容が変わったときだけ `page_links` に入れ替える（リンク先の URL とリンク文字列だけで、本文は残さない）。

- 初回は起点が約2,400個増え、約2,400件を取る（約1,200件は404）。1ホストでは最大で約210件、2秒間隔で約7分
- 2回目も、初回とほぼ同じ約2,400件を取る。404 の一覧ページは3回続けて404を見るまで `deleted` にならず、その間は削除候補の間隔（7日）で
  取り直す。403 も生きた一覧ページも、初めの間隔は7日
- 3回目もまだ約1,200件を超える（404 の3回目と、変わった生きた一覧ページ）。そのあと、週に約1,100件前後に落ち着く。
  生きた一覧ページのうち、変わったものを毎週、残りを2週に1回取る
- 1ホストあたりの件数は、どの回も初回の最大（約210件、約7分）を超えない。120分の上限にも余裕がある
- 資源が `deleted` になった一覧ページは、90日ごとに取り直す。403 は7〜30日
- 起点でなくなったディレクトリ（判定で主たる URL が差し替わった、など）の行は、`status = 'retired'` にして巡回から外す。行と履歴は残り、また起点になれば `queued` に戻る。
  制度の URL（`program_urls`）に使われている行は外さない
- 主たる URL が1件も無いとき（取り込みの失敗や接続先の取り違え）は、何も書かずにエラーにする

API が返すものは変わらない。一覧ページは制度の URL（`program_urls`）には入らない。
ただし、人の判定（`apply-reviews link` の `hit`・`index`）で一覧ページが制度の URL になったときは、その行は `seed` に変わり、
制度の URL として巡回される（[apply-reviews.md](apply-reviews.md)）。

一覧ページのリンクは、一覧ページの URL で取ったときに入れる。制度の URL と同じ資源に当たる一覧ページは、制度の URL で取ったときも、
リンクが変わっていれば入れ替える（古いまま残さない）。

### 取る間隔

週1で回すので、URL ごとの間隔は次のように丸まる:

| 間隔 | どの URL か | 実際に取られる週 |
|---|---|---|
| 3.5日 | 内容が変わったページ | 毎週（最短の3日は、週1では効かない） |
| 7日 | 初めて取ったページ・前回と比べられなかったページ | 毎週 |
| 10.5日 | 変わらなかった1回目 | 2週後 |
| 14日 | 変わらないページの上限 | 2週に1回 |
| 15.75日 | 取れない（403・robots）ページの3回目 | 2週後 |
| 30日・45日 | PDF | 4〜5週後・7週後（30日は48時間の境目に乗るので、初回を取った時刻で決まる） |

変わらないページは同じ日に取り始めているので、取得の多い週と少ない週が交互に来る。
少ない週に取られるのは前の週に変わったページが中心なので、内容の変更率が高く出る。本文のハッシュが毎回揺れるホスト
（練馬区の約90ページ）が残っている間は、少ない週に「変更率50%超」の警告が立つことがある。
一覧ページは週に2〜3割変わるので、変更率には数えない（ほかの警告は、一覧ページも含めて数える）。

## 実行サマリーで見るもの

実行サマリー（`GITHUB_STEP_SUMMARY`）には、次が加わる。

- 「一覧ページ」の表（`crawl`）: 取得・200・304・404・410・403・リンクを入れ替えた一覧ページの数。ホストごとの表と404の表は、制度の URL だけを数える。初回は404が約1,200件出る
- 「移転先の候補」の表（`suggest-moves`）: 対象の制度（主たる URL が `deleted`・`deletion_candidate`）・まだ確かめていない候補がある制度・候補の延べ・
  4件目以降を切った制度・確かめ済みとして外した候補・起点の規則が使えないホスト

「起点の規則が使えないホスト」は、一度でも取りに行った起点が5個以上で（まだ取りに行っていない起点は数えない。403 だけが返る起点は数える）、
生きた一覧ページが0のホスト。
そのホストでは親ディレクトリが一覧にならないので、候補が出ない。警告ではなく、ホストと起点の数を並べるだけ。
増えたら、深さを広げるなど起点の作り方を見直す材料にする。

## 月に1回の確認

月の最初の定期実行の後に、実行サマリーの「まだ確かめていない候補がある制度」の数を見る。0なら何もしない。
1件以上なら、候補のファイルを取って判定し、判定のファイル（`data/reviews/<日付>-moves.json`）を PR にして、`Apply reviews` を流す。
手順は [apply-reviews.md](apply-reviews.md) の「候補を取る」。候補が出ても、ジョブは失敗にならない。

## 失敗に気づく

ジョブが失敗すると GitHub が通知する。`schedule` で起きた実行の通知は、ワークフローの cron を最後に変えた人に届く
（GitHub の通知の設定で、Actions の失敗を受け取るようにしておく）。

| 失敗の形 | 見る場所 |
|---|---|
| 警告に当たって終了コード1（巡回そのものは終わっている） | 実行サマリーの「警告」。`crawl_runs` の `alerts` にも残る |
| 途中で止まった（DB に繋がらない・記録に失敗した） | ジョブのログ。`crawl_runs.finished_at` が空のまま |
| 120分で打ち切られた | ジョブが `cancelled`。同上 |
| ジョブが `Queued` のまま進まない（ランナーが来ない） | CodeBuild のプロジェクト `seido-data-hub-crawl` のビルド履歴と webhook の条件、GitHub との接続の状態（[crawl-runner.md](crawl-runner.md) の 4・7）。`crawl_runs` に行はできない |

ランナーが来ないジョブは、24時間待ってから終わる。それまで通知は届かないので、定期実行の朝は、ジョブが動き出したかを Actions の画面で見る。
来ていなければ、待ったままの実行を取り消してから（`gh run cancel <id>`）原因を直し、流し直す。残しておくと `concurrency` で後の実行も待たされる。

ログは Actions のジョブのログに加えて、CloudWatch Logs（東京、ロググループ `/aws/codebuild/seido-data-hub-crawl`）にも30日残る。

警告は、429・5xx の急増／全件失敗／内容の変更率50%超／lease 切れの多発／応答が1件も無い（`--min-responses 1`）／
ホストごと見送った（robots.txt が読めない）。
「応答が1件も無い」は、接続先の DB が空だったり、時刻の来た URL が1件も無かったりして、何も取らずに終わる実行を拾う。
「ホストごと見送った」は、robots.txt が通信エラーか 5xx で読めなかったホストごとに1件立つ。そのホストの残りの URL は
時刻を1日後にそろえて次の実行に回す（状態は変えないので、利用者に見えるものは変わらない）。一時的な障害なら次の実行で消える。
続くときは、そのホストに手元から繋がるか（TLS の方式など）を確かめる。

## 流し直す

```bash
gh workflow run crawl.yml
```

- `link-related` は何度流してもよい。既にある URL の行は触らず、死んだ制度の関連 URL（`program_urls` の行）だけを作り直す
- 途中で止まった実行が取りかけていた URL は、lease（10分）が切れてから次の実行が拾う
- 前の実行が動いている間に流すと、終わるまで待たされる（`concurrency` グループ）。待てるのは1件だけで、
  さらに流すと、待っていた実行は取り消される。二重取得そのものは claim と lease が防ぐ
- 定期実行の最中に、手元から本番の DB へ `crawl` を流さない。同じホストに同時に1件までは DB の条件で守られるが、
  同一ホスト2秒の間隔はプロセスの中でしか守られない
- 巡回の直後に流し直すと、時刻の来た URL が無いので「応答が無い」の警告で失敗する（正しい動き）

## 止める・米国のランナーに戻す

- Actions で実行を取り消すと、CodeBuild のビルドも止まる。止まらずに残ったら、CodeBuild のビルド履歴から止める
  （同時に1つまでなので、残ったビルドがあると次の実行が待たされる）
- 米国の GitHub のランナーに戻すには、`crawl.yml` の `runs-on:` を `ubuntu-latest` に戻す。データは壊れない
  （米国からだと DB との往復で遅くなり、件数の多い週は120分に近づく）

## 毎週出るもの（失敗ではない）

- 北区（`www.city.kita.tokyo.jp`）: 許可リストの外のホストへ転送されるので、範囲外として止まる
- 「起点の規則が使えないホスト」に並ぶ三鷹・足立・東村山・小平・北区・新島・八丈: 親ディレクトリが一覧にならず、生きた一覧ページが無い（測定で確かめた）。警告ではない
- 移転先の候補: 「まだ確かめていない候補がある制度」が1件以上でも、ジョブは失敗にならない（終了コード0）
- 初回の一覧ページ: 404が約1,200件出る（上の「一覧ページ」の表）

## `schedule` が止まる

公開リポジトリでは、60日間リポジトリに動きが無いと `schedule` が無効になる（GitHub の文書の記載）。
無効になったら、Actions の画面でワークフローを有効に戻す。
