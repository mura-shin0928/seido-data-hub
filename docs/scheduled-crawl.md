# 定期実行（週1の巡回）

## いつ・何が動くか

毎週月曜 03:17 JST に、GitHub Actions の `Crawl`（`.github/workflows/crawl.yml`）が本番（Supabase）の DB に対して
`pipeline crawl` を流す。Actions の `schedule` は混み具合で起動が遅れることがある。

実行は `crawl_runs` に残る。`kind` は、`schedule` で起きたものが `scheduled`、手で流したものが `manual`。

## どの URL が取られるか

時刻（`urls.next_crawl_at`）の来た URL と、48時間以内に来る URL（`--due-within-hours 48`）。
次の時刻は「取得した時刻 + 間隔」なので、余裕が無いと、今週の起動が先週より数分早いだけで7日間隔の URL が
「まだ」になり、次の週まで待つことになる。48時間は、起動のずれと、失敗に気づいて翌日に流し直したぶんのずれを吸収する幅。
再試行を待っている URL には当てない（バックオフと `Retry-After` はそのまま守る）。

週1で回すので、URL ごとの間隔は次のように丸まる:

| 間隔 | どの URL か | 実際に取られる週 |
|---|---|---|
| 3.5日 | 内容が変わったページ | 毎週（最短の3日は、週1では効かない） |
| 7日 | 初めて取ったページ・前回と比べられなかったページ | 毎週 |
| 10.5日 | 変わらなかった1回目 | 2週後 |
| 14日 | 変わらないページの上限 | 2週に1回 |
| 30日・45日 | PDF | 4週後・7週後 |

変わらないページは同じ日に取り始めているので、取得の多い週と少ない週が交互に来る。

## 失敗に気づく

ジョブが失敗すると GitHub が通知する。`schedule` で起きた実行の通知は、ワークフローの cron を最後に変えた人に届く
（GitHub の通知の設定で、Actions の失敗を受け取るようにしておく）。

| 失敗の形 | 見る場所 |
|---|---|
| 警告に当たって終了コード1（巡回そのものは終わっている） | 実行サマリーの「警告」。`crawl_runs` の `alerts` にも残る |
| 途中で止まった（DB に繋がらない・記録に失敗した） | ジョブのログ。`crawl_runs.finished_at` が空のまま |
| 120分で打ち切られた | ジョブが `cancelled`。同上 |

警告は、429・5xx の急増／全件失敗／内容の変更率50%超／lease 切れの多発／応答が1件も無い（`--min-responses 1`）。
最後のものは、接続先の DB が空だったり、時刻の来た URL が1件も無かったりして、何も取らずに終わる実行を拾う。

## 流し直す

```bash
gh workflow run crawl.yml
```

- 途中で止まった実行が取りかけていた URL は、lease（10分）が切れてから次の実行が拾う
- 前の実行が動いている間に流すと、終わるまで待たされる（`concurrency` グループ）。二重取得そのものは claim と lease が防ぐ
- 定期実行の最中に、手元から本番の DB へ `crawl` を流さない。同じホストに同時に1件までは DB の条件で守られるが、
  同一ホスト2秒の間隔はプロセスの中でしか守られない
- 巡回の直後に流し直すと、時刻の来た URL が無いので「応答が無い」の警告で失敗する（正しい動き）

## 毎週出るもの（失敗ではない）

- 町田市の子育てサイト（`kosodate-machida.tokyo.jp`）: TLS の方式が合わず robots.txt が読めないので、毎回見送る
- 北区（`www.city.kita.tokyo.jp`）: 許可リストの外のホストへ転送されるので、範囲外として止まる

## `schedule` が止まる

公開リポジトリでは、60日間リポジトリに動きが無いと `schedule` が無効になる（GitHub の文書の記載）。
無効になったら、Actions の画面でワークフローを有効に戻す。
